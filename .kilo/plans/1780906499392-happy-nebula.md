# Plan: Allow Identification-Only Brands to Define & Collect Tokens

## Problem

Identification-only brands (e.g. `ID_ONLY_BRAND`) finalize immediately after party resolution — **no tokens are collected**. Even when `levelRules` could define tokens to ask, the identification flow skips directly to `AUTHENTICATED at NONE`.

**Expected behavior:** Identification-only brands should define token rules via `levelRules[NONE]`. These tokens are collected from the caller, and **each token value is matched against the matched party's fields** to confirm identity. Only when all configured tokens pass party-field verification does the session finalize as `AUTHENTICATED at NONE`.

Key behaviors:
- **Single-party ANI** → collect tokens → match against that party's fields → confirm → finalize
- **Multiple-party ANI** → disambiguation narrows to one party → collect tokens → match → confirm → finalize
- **No `levelRules` defined** → backward compatible: finalize immediately after party resolution

---

## Design Decision

Use the **existing `levelRules` structure** with a `NONE` level key to define identification token paths. This reuses the proven `evaluateProgress()` / `submitToken()` pipeline.

Add a **party-field verification gate** in `AuthEngine` that activates for identification-only brands: after format validation, the token value is checked against the matched party's corresponding field (e.g., `ACCOUNT_NUMBER` → `Party.accountNumber`). This ensures tokens contribute to identity confirmation.

### 5. `AuthEngine` — Add party-field verification for identification-only brands

**File:** `src/main/java/com/yourco/ivr/engine/AuthEngine.java`

Add a new method `verifyAgainstParty()` and a `partyFieldMap` (mirroring `DisambiguationEngine.tokenFieldMap`). Insert it between Stage 1 (format gate) and Stage 2 (backend gate) in `validateExternally()`.

**TokenType → Party field mapping:**
| TokenType | Party field |
|---|---|
| `ACCOUNT_NUMBER` | `Party.accountNumber` |
| `DATE_OF_BIRTH` | `Party.dateOfBirth` |
| `SSN_LAST4` | `Party.ssnLast4` |
| `CARD_LAST4` | `Party.cardLast4` |
| `PIN`, `OTP`, `VOICE_PRINT` | *No party field — skip party verification for these* |

```java
private ValidationResult verifyAgainstParty(IvrSession session, TokenType tokenType,
                                            String tokenValue) {
    Party party = session.getMatchedParty();
    if (party == null) return ValidationResult.ok();

    Function<Party, String> extractor = partyFieldMap.get(tokenType);
    if (extractor == null) return ValidationResult.ok(); // no field mapping → skip

    String expectedValue = extractor.apply(party);
    if (expectedValue == null) return ValidationResult.ok(); // no data to match against

    if (tokenValue.equals(expectedValue)) {
        return ValidationResult.ok();
    }
    log.info("PARTY_VERIFY [{}] token={} value mismatch for party={}",
        session.getSessionId(), tokenType, party.getPartyId());
    return ValidationResult.fail(ValidationErrorCode.VERIFICATION_FAILED);
}
```

Insert into `validateExternally()` after the format gate succeeds, before the backend gate (or skip party check if the token type has no party field).

**Party verification activation rule:** Only run when `config.isIdentificationOnly()` is true. Regular brands skip this gate (they use backend lookup services instead).

### 10. Transfer disambiguation tokens to validatedTokens (avoid double-prompting)

**File:** `src/main/java/com/yourco/ivr/engine/AuthEngine.java`

When identification-only with NONE-level rules, after disambiguation resolves a single party, the tokens submitted during disambiguation are in `collectedTokens` but NOT in `validatedTokens`. If a disambiguation token (e.g., `ACCOUNT_NUMBER`) is also a required token in the NONE path, the caller would be prompted for it again.

Fix: In `onPartyResolved()`, for identification-only with NONE rules, scan `collectedTokens` and add any token whose type matches a required token in the NONE path to `validatedTokens`. This avoids redundant re-prompting.

```java
// In onPartyResolved(), before calling evaluateProgress():
if (config.isIdentificationOnly() && config.getLevelRules().containsKey(AuthLevel.NONE)) {
    LevelRule noneRule = config.getLevelRules().get(AuthLevel.NONE);
    // Transfer disambiguation tokens that match required identification tokens
    for (TokenType collected : session.getCollectedTokens().keySet()) {
        for (TokenPath path : noneRule.getPaths()) {
            if (path.getRequiredTokens().contains(collected)) {
                session.getValidatedTokens().add(collected);
                break;
            }
        }
    }
    return evaluateProgress(session, config);
}
```

## Edge Cases Covered

1. **ID-only + no `levelRules`** → `onPartyResolved()` calls `finalizeIdentification()` immediately (backward compat)
2. **ID-only + `NONE` rules + single party** → collect tokens, verify against party fields, finalize on path complete
3. **ID-only + `NONE` rules + multiple parties** → disambiguation narrows to single party → collect tokens → finalize
4. **ID-only + initialTokens** → tokens processed at start, remaining prompted
5. **ID-only + token retries/path switching** → works via existing `handleFailure()`/`advanceToNextPathOrFail()`
6. **ID-only + backup tokens** → `resolveBackupToken()` maps alternatives to required slots
7. **ID-only + escalation** → still rejected
8. **ID-only + party-field mismatch** → verification fails, retry or path switch
9. **ID-only + token type with no party field** (PIN, OTP) → party verification skipped; format check only
10. **Null `levelRules` safety** → all `getLevelRules().get(...)` calls guarded against NPE
